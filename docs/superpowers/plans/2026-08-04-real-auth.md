# Real Authentication — Plan & Implementation

**Status:** Implemented and merged into `main` (commit `069b83e`), 2026-08-04.

**Goal:** Replace the dev-login stub's role as the *only* path to a session by adding real,
password-based authentication — registration, login, refresh-token rotation, and logout — without
touching the dev-login stub itself.

## Context

Before this work, `POST /v1/auth/dev-login` (`backend/app/api/auth_dev.py`) was the only way to get
a session: it takes just an email, upserts a `User` row with no password, and issues a JWT. It was
always meant to be temporary — `backend/README.md`'s "Not yet built" list called out real
authentication explicitly, and `auth_dev.py`'s own docstring says it's meant to be "replaced by the
auth plan."

Decided with the user before implementation:

- **Scope:** registration + login + refresh tokens + logout. No email verification, no password
  reset — both need email-sending infrastructure that doesn't exist yet, and were explicitly ruled
  out of this pass.
- **`/v1/auth/dev-login` stays completely unchanged**, living alongside the new real routes rather
  than being replaced. It's used by the local docker-compose dev loop (`backend/README.md`) and by
  test fixtures (`backend/tests/conftest.py`'s `user`/`auth_headers`). This overrides the original
  "replaced by the auth plan" intent in `auth_dev.py`'s docstring — a deliberate choice, not an
  oversight.

## Design decisions (and why)

**`User.hashed_password` is nullable**, not `NOT NULL`. `auth_dev.py` creates users with no
password at all and had to stay untouched — a non-nullable column would break every dev-login
insert. `NULL` means "this account has no password credential" (a dev-login-created account, or
later, an SSO-only one). `authenticate_user` treats a `NULL` hash the same as a wrong password: a
generic 401, so there's no way for a caller to learn from the response that an account exists but
has no password. This also means the existing `user`/`other_user` test fixtures needed **zero
changes** — they already omit the field.

**Refresh tokens are opaque random strings, not JWTs.** Each is `secrets.token_urlsafe(32)` (256
bits of entropy), and only its SHA-256 hex digest is ever stored (`refresh_tokens.token_hash`) — the
raw token itself never touches the database, the same principle as not storing raw passwords.
Revocation requires a database check regardless of token format, so a signed JWT refresh token would
buy nothing while adding a second signing secret to manage. SHA-256 (not bcrypt) is the right hash
here: the token already has enough entropy that a fast, deterministic hash is not a weakness, and
determinism is what makes an indexed equality lookup possible — bcrypt's per-hash random salt would
rule that out.

**Access tokens are unchanged in mechanism.** Real login/register/refresh issue access tokens
through the exact same `create_access_token`/`decode_access_token` (`app/security/tokens.py`) that
dev-login already used. `app/api/deps.py`'s `get_current_user` — and therefore every protected
route — needed **zero changes**. The only new setting is `access_token_ttl_seconds` (15 minutes),
separate from dev-login's existing `jwt_ttl_seconds` (24 hours), which was left untouched.

**Refresh-token reuse triggers a bulk revoke, not a `replaced_by` chain.** If a refresh token that
has already been rotated (its `revoked_at` is set) is presented again, every currently-active
refresh token for that user is revoked in a single query, and the caller gets the same generic 401
as any other invalid-token case. This treats replay as "assume the token was stolen, kill every
session for this user" — simpler than tracking a rotation chain, and it needs no extra column.

**Password hashing uses `bcrypt` directly**, not `passlib` (unmaintained, has broken against recent
bcrypt releases). bcrypt truncates input at 72 bytes, so `RegisterRequest`/`LoginRequest`
(`app/schemas/auth.py`) enforce `max_length=72` at the schema level rather than silently discarding
part of a longer password.

## What was built

**New files:**

| File | Purpose |
|---|---|
| `backend/app/models/refresh_token.py` | `RefreshToken` model — `id`, `user_id` (FK, `ondelete="CASCADE"`), `token_hash` (unique), `issued_at`, `expires_at`, `revoked_at` (`NULL` = active) |
| `backend/alembic/versions/0002_auth.py` | Adds `users.hashed_password` (nullable) and creates `refresh_tokens` |
| `backend/app/security/passwords.py` | `hash_password`/`verify_password` (bcrypt) |
| `backend/app/schemas/auth.py` | `RegisterRequest`, `LoginRequest`, `RefreshRequest`, `LogoutRequest`, `TokenPair` |
| `backend/app/services/auth.py` | Business logic: `register_user`, `authenticate_user`, `issue_token_pair`, `rotate_refresh_token`, `revoke_refresh_token`, `hash_refresh_token`, plus typed exceptions (`EmailAlreadyRegistered`, `InvalidCredentials`, `InvalidRefreshToken`) that the route layer maps to HTTP status codes — the same thin-route pattern as `app/services/attempts.py` |
| `backend/app/api/auth.py` | The four new routes |
| `backend/tests/test_register_login.py` | 14 new tests |

**Changed files:** `backend/app/models/user.py` (+`hashed_password`), `backend/app/models/__init__.py`
and `backend/alembic/env.py` (export/import `RefreshToken`), `backend/app/config.py` and
`backend/.env.example` (+2 TTL settings), `backend/app/main.py` (mount the new router),
`backend/pyproject.toml` (+`bcrypt`), `backend/README.md` (endpoint table, "Not yet built").

**Endpoints:**

| Method | Path | Status codes | Notes |
|---|---|---|---|
| `POST` | `/v1/auth/register` | 201, 409 (duplicate email), 422 (validation) | Returns a `TokenPair` |
| `POST` | `/v1/auth/login` | 200, 401 | Wrong password, unknown email, and a passwordless (dev-login-only) account all return the *same* generic message — no enumeration |
| `POST` | `/v1/auth/refresh` | 200, 401 | Unknown, expired, or reused token — same generic message |
| `POST` | `/v1/auth/logout` | 204 always | Idempotent — revoking an unknown or already-revoked token is a no-op |

## Verification

- **126 tests pass** (112 pre-existing, unmodified + 14 new). The 14 new tests cover: registration
  success/duplicate-email/too-short-password; login success/wrong-password/unknown-email/
  dev-login-created-account-has-no-password (with an explicit check that the unknown-email and
  wrong-password responses are byte-identical); refresh rotation, chained legitimate refreshes,
  rejecting an expired token, and reuse detection revoking the whole session family; logout revoking
  a token and being idempotent for an unknown one; and a login-issued access token authorizing a
  protected route exactly like a dev-login token — proving `get_current_user` needed no changes.
- **ruff clean** on every new/changed file.
- **Manually verified against a real running server** (not just the test client): register → a
  protected route accepted the access token → login → refresh → presenting the old refresh token a
  second time correctly 401'd → logout → refreshing the logged-out token correctly 401'd.

## Explicitly out of scope (flagged, not blocking)

- Rate limiting on `/login`/`/refresh` — no such library exists in the project yet.
- `auth_dev.py` remains a live, unauthenticated account-takeover primitive for any email,
  unconditionally mounted. Pre-existing behavior, deliberately left untouched per the scope decided
  for this pass — worth revisiting before any production deployment decision.
- No `GET /v1/auth/me` endpoint — wasn't part of the agreed scope; a natural small follow-up once
  frontend work needs to know who's logged in.
